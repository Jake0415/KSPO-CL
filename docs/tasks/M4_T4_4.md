# M4.T4.4 — Frontier 기반 동시 BFS 크롤 (run_incremental·enqueue_seeds 리팩토링)

> **상태**: 보류(deferred) — M4.T4.1 머지 후속 작업으로 신설.
> **선행**: M4.T4.1 (run_incremental + 내부 링크 추출) 머지 완료.

## Goal

현재 `enqueue_seeds`/`run_incremental`이 inline 시리얼 iteration으로 페이지를 처리한다.
1000+ 페이지 도메인에서 incremental 1회가 분 단위 소요되며, 같은 worker 프로세스가
fetch+clean+refine+chunk를 순서대로 막힘 없이 깔리게 만든다.

본 Task는 [crawl/frontier.py](../../src/kspo_ingest/crawl/frontier.py)의 Redis 기반
URL 큐를 전 파이프라인에 도입하여 **fetch_page를 ARQ 작업으로 분리**, 동일 도메인
rate_limit를 지키며 multiple workers가 병렬 처리하도록 만든다.

## 잔여 컨텍스트 (M4.T4.1에서 보류)

1. **inline iteration**: `run_incremental._process_one`이 `await fetch_page → clean →
   refine → chunk_and_index`를 시리얼로 호출. M4.T4.1 Risk에서 명시.
2. **신규 URL 발견**: `extract_links`가 내부 링크를 `pages.status='DISCOVERED'`로
   upsert하지만, 같은 incremental Job 실행 중 발견된 URL은 다음 Job에서야 처리됨.
   Frontier 도입 시 같은 Job 내에서도 enqueue 가능.

## Spec

### `process_url` ARQ task

```python
async def process_url(ctx, *, job_id: int, domain_id: int, url: str, depth: int) -> None:
    """frontier에서 dequeue된 1 URL을 fetch→clean→(skip|refine→chunk) inline 체인.

    enqueue_seeds/run_incremental의 _process_one 로직을 ARQ task로 분리하여 worker
    concurrency가 자연스럽게 적용되도록 한다.
    """
    page_id = await fetch_page(ctx, job_id=..., domain_id=..., url=..., depth=depth)
    if page_id is None: return
    cleaned = await clean_page(ctx, ...)
    if cleaned is None or cleaned.get("skipped"): return
    await extract_links(ctx, job_id=..., page_id=page_id)
    refined = await refine_page(ctx, ...)
    if not refined or not refined.get("refined"): return
    await chunk_and_index(ctx, ...)
```

### `enqueue_seeds` 리팩토링

```python
async def enqueue_seeds(ctx, *, job_id: int, domain_id: int) -> None:
    domain = ...; await start_job(...)
    seed_url = f"{domain.scheme}://{domain.host}/"
    pool = await get_arq_pool()
    await pool.enqueue_job("process_url", job_id=job_id, domain_id=domain_id, url=seed_url, depth=0)
    # finish_job은 별도 task에서 (drain 감지) — 또는 ARQ result_callback 활용
```

### `run_incremental` 리팩토링

```python
async def run_incremental(ctx, *, job_id: int, domain_id: int) -> None:
    # 기존 페이지 + root → frontier에 push
    urls = SELECT url FROM pages WHERE domain_id=? AND status != 'REMOVED'
    pool = await get_arq_pool()
    for url in urls + [root_url]:
        await pool.enqueue_job("process_url", job_id=job_id, domain_id=domain_id, url=url, depth=0)
```

### Frontier 강화

기존 `crawl/frontier.py`는 단순 set이라면 다음을 추가:
- depth 우선순위 정렬 (BFS)
- 같은 url_hash dedup
- domain별 분리 키 (서로 다른 도메인의 동시 Job 격리)

### Job 종료 시점 결정

inline iteration에서는 모든 await가 끝나면 그 자리에서 finish_job. Frontier 모드에서는
worker가 비동기 처리하므로 별도 종료 감지 필요:

| 방식 | 장점 | 단점 |
|---|---|---|
| Counter (Redis): pending++ on enqueue, pending-- on done, ==0 시 finish | 정확 | 원자성 + race condition 주의 |
| Polling (cron): 5분마다 stuck Job 확인 | 단순 | 종료 지연 |
| ARQ result_callback | ARQ 표준 | 분기별 처리 복잡 |

권장: **Counter** — Redis INCR/DECR + `pending == 0` 시 finish_job 호출.

### 동시성·rate_limit 상호작용

- worker `max_jobs=4` (현재) → 동시 4개 URL 처리
- crawl/rate_limit.py의 host별 토큰 버킷이 `acquire()`에서 대기 → 동일 도메인 4 worker가 같은 host에 몰리면 자연 직렬화
- 다른 도메인 동시 Job: 도메인별 rate_limit 키가 분리돼 있으므로 문제 없음

## 보류 사유 (M4.T4.1 시점)

- M4.T4.1의 inline 모델로도 PoC·소규모 도메인은 충분히 동작
- frontier 모델은 Job 종료 감지·counter 동기화 등 분산 동시성 고민이 필요해 별도 PR로 분리하는 것이 안전
- KSPO 본사이트 1 도메인 ~ 수천 페이지 규모에서 incremental 분 단위 소요는 운영상 허용 범위 — 트리거가 weekly cron이므로 처리 시간 자체가 중요하지 않음
